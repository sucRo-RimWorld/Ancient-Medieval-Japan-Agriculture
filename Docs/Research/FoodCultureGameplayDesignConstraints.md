# AMJ 食文化・料理OH — 現行選定ルールと議論済みの制約

**状態（2026-11-01移管）:** Agriculture所管の選定ルールと設計判断履歴（判断内容は2026-10-29時点）。Daily Menuを基盤にした料理の一膳化は作者採用済みで、Agriculture PR #281に実装・仮想環境検証がある。個別作物の採否と最終数値は未確定。旧「Daily Menu未採用」「組合せ方式未承認」は現在の判断ではない。会話で失われがちな「採用しなかった理由」を保全するための記録であり、新仕様の採用・実装指示ではない。記録できた会話範囲に限るため、過去の全議論を復元したと主張しない。

## 作物選定への適用（作者訂正・2026-10-29）

1. **作物 → 使える料理 → 大まかな全体バランス → 実装数値**の順で整理する。料理を成立させるために先に作物を仮置きしない。
2. **MO作物も中世日本への適合性で選別し、不適切な作物は通常栽培・料理・供給経路から除外する。** MOの既存作物構成を固定したまま、日本側作物だけに差別化を要求しない。既存Defを削除するかどうかは保存互換と別途判断する。
3. 葉菜は中世の代表的な食用・栽培の根拠から具体的な作物を選ぶ。抽象的な「菜類」で確定せず、CCTO等の栽培特性を調べられる対象にする。古代の存在、灯明利用、種実食、葉食、庶民への普及を混同しない。
4. [保持対象抽出表](FoodHistoricalEssential.md)は8評価行・系統であり、8食品や各野菜の採用決定ではない。大根・葉菜・越瓜・大豆・梅、追加候補の冬瓜も採用未確定。
5. [旧候補表](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/blob/main/Docs/Research/DeferredPlantsAndProcessing.md)の重複・競合による不採用／保留は履歴として再評価する。既に確認した史料・用途は未確認へ戻さない。荏胡麻は種実利用を基本とした旧案と後の保留を保持し、葉菜への採用決定へ読み替えない。

料理の採用済み方針と未決の数値は[Agriculture Design](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Agriculture/blob/main/Docs/Design.md#crop-selection-current)が所有する。一膳化の実装証拠は[Agriculture PR #281](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Agriculture/pull/281)を参照し、mainへの統合・実プレイ検証と混同しない。

## 現行選定ルール（作者決定・2026-10-28）

**適用範囲と優先関係:** 食品候補の選定・価値評価・OH要否判断については本節を正本とする。下記2026-10-26の判断履歴のうち、全食品への固有性能要求、同性能を理由とする除外、食事効果の一律否定と読める部分は本節で更新する。歴史資料の正本は[食品連鎖台帳](FoodProcessingChainAudit.md)、調査進捗は[小作業マップ](FoodAuditWorkMap.md)に保持する。これは選定ルールの更新であり、B/C/D調査の完了、個別食品の採用、OH実施の承認ではない。

### 判断の順序

| 段階 | 判断と成果 |
|---|---|
| ① 食文化による選定 | **中世日本の庶民の食文化を重視する。** 主食・副食・保存食・携行食・季節食などの位置づけを、年代・製法・地域・階層・普及の根拠とともに確認する。古代の記載や上層階級の料理を中世庶民へ一般化しない。候補、条件付き候補、史料不足による保留、対象外を分け、「欠けると何の文化的表現が失われるか」を記す。 |
| ② 現行RimWorldでの料理・食事上の価値評価 | Vanilla・MO・既存AMJの実装を照合し、簡素な食事システムでの用途、性能、食事効果、代替関係と、原料調達から消費までの総負担を評価する。表現できる価値と不足する表現を記録する。**価値が薄いという理由だけで、この段階で不採用・料理への内包を確定しない。** |
| ③ システムOHの要否判断 | ②の結果を受け、表現できない部分の重要性、既存機能で対応する案との違い、システム変更による改善、開発・保守・操作・互換性の負担を比較する。OHしない／必要性を認めて設計検討／保留を区別する。**OHで役割を作れることは、OHすべき理由の証明ではない。** |
| ④ 採否・実装方法の決定 | 現行機能で追加、同性能で文化を表現、既存機能への統合、工程や中間品を料理へ集約、承認されたOHによる実装、保留・不採用を比較する。確定した仕様・数値は所有ModのDesignへ移す。 |

**①の歴史重要度による絞り込み結果は、別文書[食品の歴史重要度による選定結果](FoodHistoricalSelection.md)に記録する。** 原台帳は史料・歴史判断、本書は選定ルール、専用文書は候補別の選定結果を保持し、重複した結果表を作らない。②以降のゲーム評価・OH判断を歴史重要度の判定に混入させない。

原台帳のA–Dは歴史調査、Eは既存Mod照合、Fは実装判断の枠組みとして維持する。①はA–Dの証拠から選定し、②はEの実ソース照合を用いる。Fでは②の価値評価結果→③OH要否→④採否・表現方法の順序を守る。既存のB/C/D未完を完了扱いせず、未確認を明記する。

### 文化的保持とゲーム効果

- **性能が既存食品と同じでも、中世日本の庶民の食文化として存在しないことが不自然なら残す。** 全料理への固有性能・代替不能性を要求しない。ただし、どの食品が該当するかは個別に根拠を確認し、現代の知名度だけで認定しない。
- 食品を残すことと、原料・中間品・副産物・完成料理・全工程を独立実装することは別。文化的保持対象の表現方法も③の後に比較し、同性能であることだけをOHの理由にしない。
- **食事による臓器への良い影響は、MOで実装されているものと同程度まで許容する（作者決定）。** ②の評価に含められるが、全食品への付与や具体的な効果の承認ではない。具体化前にMOの実ソースで効果量・持続時間・重複・摂取頻度などを確認し、「同程度」の比較根拠を示す。本更新ではMOの効果を独立検証していない。
- 保存・携行・物流上の価値は食品や加工経路の評価として扱えるが、それだけを料理・食事OHの価値へ付け替えない。OHが複数の食品・経路に共通して有効かは評価観点であり、必須条件ではない。対象が限定されても重要性と負担で比較する。

### 大豆・小豆・調味料の重点確認

- 大豆・小豆は、他の作物から食事を作る経路も含めて比較する。「その作物を使う理由」と「特定の加工品を作る理由」を分ける。加工先やレシピの数だけでは価値を証明しない。
- 生大豆を食べられなくすることは作者が許容した選択肢であり、採用決定ではない。生食禁止や加熱の必須化は利用条件・負担を増やすだけで、豆腐等への追加加工を選ぶ利点を自動的には生まない。小豆についても必要な処理と追加加工の価値を区別する。
- 味噌・醤油などの調味料、酢・油は、文化的重要性に対してRimWorldで独立資源としての存在意義を持たせにくい重点検討対象。調味、加工・調理、実際に対象とする他用途を分け、「使う料理がある」「必須材料にすれば需要がある」だけで価値を認定しない。
- これらを先に除外せず、独立アイテム化・料理への内包・効果付与・OH対象化のいずれも先取りしない。まず①②を行い、③を経て④で判断する。役割を作るためだけの別産業追加や未承認の効果量産をしない。

**現在の未決定事項:** 個別作物・料理の採否、製法の抽象化、性能値、個別効果の加算・重複。Daily Menu基盤とAgricultureによる一膳化の採用は再審議しない。

## 問題の定義（2026-10-25〜26 作者の繰り返しの指摘）

- RimWorldでは完成料理が主に栄養量、食事品質、心情などに集約される。史実に合う料理名・素材・調理工程を増やしても、それだけでは**食事の選択、消費、評価というゲームプレイ**に差が生じない。
- 加工品を別ThingDef／レシピに分けられるという技術的可能性と、プレイヤーが加工する価値が生じることは別問題。通常食事へ投入した段階で素材ごとの差が見えにくい。
- 料理の数を増やした結果、最適な料理だけを量産し、その他は使われなくなる構造を解決できていない。史実再現のための追加作業・運搬・在庫・Bill管理が利益を上回る恐れがある。
- **保存性は料理OHの価値として評価しない。** 塩蔵・乾物は料理OHとは別の保存加工領域であり、そちらでは保存期間・労力・素材損失等の比較が独立の設計課題になる。
- **設計を確定する前の試験・シミュレーションは、この問題の検証にならない**。具体的な利益とプレイヤーの選択が定義されないまま、仮定したボーナスや食事時間の比較を「設計の検証」と称しない。

## 大豆加工と保存性の区別（2026-10-26 作者訂正）

- **乾燥大豆はそのまま長期保存できる原料**であり、豆腐・豆乳のような水分の多い加工品へ変えると、通常は原料の乾燥大豆より保存性が低下する。大豆加工を「保存性を向上させるための工程」と説明しない。
- 味噌・醤油等の発酵調味料には個々の保存特性があるが、**乾燥大豆から加工すれば一律に保存性が上がる**という説明は成立しない。各品の実際の用途や食文化上の意味と、保存加工の利点を分けて扱う。
- 豆腐・味噌等の加工と、塩蔵・乾物の**保存手段としての独立した価値**は別の設計論点。保存性を料理OHのメリットに付け替えない。

## 外部Modについての混同を防ぐ

- **RimCuisine 2** は実際に保存食の保存性・携帯重量、通常レシピへの利用、嗜好品などの数値を設定している。公開1.6 Defでは乾燥肉30日・乾燥果物60日・漬物120日という腐敗開始設定も確認できる（[公開ソース](https://github.com/emipa606/RimCuisine2Core/blob/main/1.6/Defs/RC2_ThingDefs/RC2_Items_SurvivalFood.xml)）。ただしこれらは主に**保存加工Modとしての価値**の例であり、料理OHの価値を立証しない。
- **数値的利益が存在することは、その仕組みが料理OHの問題を解くことと別**。2026-10-26 のエージェント回答は、保存性という別領域の効用と料理OHのゲーム的価値を混同していた。保存加工自体の利点の是非は当該領域の設計で判断する。
- **Daily Menu** は採用済みの基盤。保存した各料理を喫食時に一膳へまとめるAgriculture側実装はPR #281を参照する。役割別の品数判定・調味料効果等の残課題を、基盤の採用可否へ戻さない。
- VGP、Vanilla Cooking Expanded、CulinaryCraft等も機能の存在とAMJに導入する価値を分けて比較する。既存Modの探索は [ExistingModAudit](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/blob/main/Docs/Research/ExistingModAudit.md) に従う。

## 他Ownerの既存方針を保持

- Agriculture/旧Grainsは**少数の抽象化した日常料理を基礎**とし、料理名の差だけでRecipeを増やさず、材料・加工の選択が意味を持つ料理や特別食を別途検討してきた。公開内容・既存数値・実装責務を本記録では変更しない（[Agriculture Design](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Agriculture/blob/main/Docs/Design.md)）。
- 発酵・醸造・塩蔵保存は別の [候補研究](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/blob/main/Docs/Research/FermentationBrewingPreservationCandidate.md) で扱う。**塩蔵・乾物の保存上の利益は、それ自体が独立した評価対象**であり、料理OHへ移して価値を説明しない。発酵調味料の存在も料理OHの価値を自動的に証明しない。
- 食事に対する社会・身分的な心情は既存Cultureの責務と重なる場合がある。一般的な料理OHのOwnerを、根拠なくCultureやAgricultureに一括移管しない。

## 旧・再開時の条件・未解決事項（2026-10-26の履歴）

**現在の再開順序は上記「現行選定ルール」に従う。** 以下は料理OH自体の検討に入った場合の旧論点であり、食文化の選定と現行システム評価を飛ばしてOH設計を始める指示ではない。

1. **料理OHにおいてどのプレイヤー上の意思決定が不足しているか**を定義する。料理名、在庫やレシピの件数、別領域の保存日数、心情数値を成果指標の代用にしない。
2. RimWorld標準の食事の仕組みでそれが成立するか、食事評価機構を別途必要とするかを**基本設計として比較**する。この記述は2026-10-26当時の未承認状態。現在のDaily Menu基盤・一膳化は採用済み。
3. 料理OHで増える労働・調理・運搬・在庫管理の負担に見合うかを比較し、成立しない案は見送る。独立した塩蔵・乾物の保存バランスと混同しない。技術調査とテストはその判断に必要な範囲だけ行う。
4. **作者が承認する前に**依存Mod、追加加工品、バフ、料理構成、テスト計画を確定しない。

**記録の境界:** 本書は2026-10-28の現行選定ルールと、2026-10-26時点で追跡できる反論・判断理由を保持する。過去のすべての却下理由を網羅する完成設計書ではない。今後、判断が覆る場合は**何が新たに確認され、従来の反論のどこが解消したか**をこの正本と採用先Owner文書の双方で更新する。チャット内の記憶だけを正本にしない。
