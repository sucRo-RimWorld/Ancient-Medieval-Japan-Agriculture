### 原料から料理までの接続を監査する時の扱い
- **原料・加工品・料理・消費目的の四層を区別。** 同一の原料が別の中間品を経る経路（豆乳→豆腐／湯葉、米→飯→糒、炒麦→粉）を混ぜない。
- **加工後の食品と保存という用途を別にする。** 「乾物」「兵糧」「料理」は広い用途なので品目として二重計上しない。乾飯の実装価値は作者判断を維持。
- **麹・酒粕・おから・米糠などの副産物・中間品**を扱う場合は、原料取得、発生量、最終消費先がつながるかを個別調査。現段階で実装は要求しない。
- **史料が必要な部分は不確実として残す。** とくに海藻の後世加工、甘味料の現代形態、菓子、香辛料、食肉・乳製品の普及、独立醤油製造を中世の確定項目としない。
- **Mod照合とコスト評価は段階E・Fに留保。** 本表は食文化史の洗い出しを目的とし、ゲーム内での性能差を記入していない。

- B09（糸引納豆）：史料例は冬季に集中し、歳暮の贈答品としての流通が認められる。贈答元は近江国、とくに湖東地方が多いという研究報告がある。直接の製法・菌種・出荷量はこの抄録のみでは断定できない。
- B10（唐納豆／塩麹を用いた系統）：季節を問わず見られ、嗜好品・手土産として扱われた。糸引き納豆の単純な保存期間違いではなく、**発酵・塩・麹・食べ方が異なる別枝**として継続調査する。
- この研究は、従来の「納豆＝寺納豆」という大づかみの分類では時代・流通差を取り落とすことを示す。ただし、製造工程と日本全国の普及率は未確定。

### 乾飯と焼米は別工程
- [小学館『日本大百科全書』「糒」](https://kotobank.jp/word/%E7%B3%92-629846)によると、**糒＝煮る／蒸した米飯を乾燥する保存食**で、水・湯で戻す。兵士備糒の法令にも言及する。
- 同項に引かれる『世界大百科事典』の携帯食糧解説では、**焼米＝籾を炒って殻を除く**加工として記載。旧G07/G12/G13では「炒米・焼米・こがし」の粒度が混在していたため、以下の独立枝にする。
  - G06：米→炊飯／蒸飯→乾燥→**糒・乾飯**→備蓄・携行
  - G13内の別枝：籾→炒る→籾殻除去→**焼米**→携行・そのまま／復水で食べる
  - G07：麦などの穀粒→炒る→粉砕→**こがし・はったい粉**→粉食／携行候補（こちらは中世の品目・製法別に史料照合が必要）
- この分離は歴史の製法検証のためであって、三食品の独立アイテム化やゲーム効果の採用ではない。

### 漏れの具体的な修正と再発防止の対象（手順自体は変更しない）
- **「魚介→生食」は単一種に限定できない**。12世紀の上層饗応で鱸・鯛・鮎・鯉・蛸が列挙されるが、魚種間で加工・保存工程は一致しない。P01を包括カテゴリとして維持し、史料ごとの品目名を食品候補として紐づける。
- **「魚の保存食」「植物の乾物」は後代の名産品一覧から無条件に中世へ転用できない。** 近世初期の『毛吹草』を用いたリストは中世に存在した可能性を探る索引に限定する。
- **糒／焼米は古代・中世の別史料に独立根拠がある**ため、『毛吹草』の記載だけで検証したことにしない。
- **専門資料の対象・年代を同じ表で明記する**。2014年に刊行された研究に掲載された1645年頃の名産品を、1400年代の生産実態として報告しない。
- 魚介類については琵琶湖博物館の2010年報告第25号のpp.17–174に、15世紀の山科家の日記由来の供給・消費記録・データベースと中近世鮒料理史料が分かれている。**本文の全数読み取り未完了のため、網羅率を提示しない。**

**D網羅判定：未達。** 今回確認できたのは年代付きの原料供給・上層食事と、**中世史料として扱ってはいけない江戸初期の品目群**である。採用判断・Mod比較は行わない。

### Bの空白を埋めるための分岐チェック（食品群間を接続）

- **海藻→煮る／酢で和える**：荒布煮・差酢若布。単なる昆布出汁と乾海藻の販売だけにしない。
- **茸→調味加熱**：酒煎松茸・平茸雁煎。茸を「乾燥保存」と「汁の具」だけにしない。
- **野菜→特殊な切り方・酢・煮染**：繊羅蔔・煮染牛房・酢漬茗荷・茄子酢菜・黒煮蕗。
- **大豆→加工品→二次料理**：豆腐羹・納豆・煎豆。豆腐を豆乳凝固だけで経路終了にしない。
- **動物名を含む精進料理**：鼈羹・猪羹・平茸雁煎は見立ての可能性を区別。料理名から肉の使用量を捏造しない。
- **穀粉→粉食／油脂加工／包葉**：索餅・煎餅・唐菓子・粽。蒸す・茹でる・焼く・揚げるを独立した加工にする。
- **調理済みの米→別加工**：糒（飯の乾燥）、焼米（籾を炒って脱殻）、油炒り米（油で炒る）。名称の類似だけで併合しない。

### Cの調査境界
1. **確認済み（名称）と確認済み（製法・用途）は別。** 料理名に「煮」「酢」「酒」などが含まれていても配合と手順は別の証拠が必要。

3. **後世の料理本による復元**は後世の証拠。Bに並んだ候補をCの検証前に削除・採用しない。
4. 現段階のCの対象は上表と先行資料調査で裏付けた品目に限定する。全品目に判定済みと表示しない。Dの最終網羅判定・E/FのMod実装評価には進まない。

## C年代検証：奈良・平安期の植物油を種類・用途別に区別（2026-10-27）

奈良文化財研究所の研究で、『正倉院文書』『延喜式』等に現れる植物油は以下の七種類と整理されている。**古代史料に油名があることと、当該油が食用に使われたことは別の命題**である。

| 荏油 | エゴマ種子 | 古代の油名として記載。灯明・食用等の用途を各史料ごとに分ける |
| 麻子油 | アサ種子 | 古代の油名と貢納記録。食品加工に使われたと個別には未確認 |

## C年代検証：古代の果実・木実記録と食用／栽培の区別（2026-10-27）

『正倉院文書』『延喜式』に植物名が列挙されていても、**庭園栽培、採集、貢納、菓子としての供食**は異なる。中村太一「日本古代の街路樹」の史料整理をもとに、Bにある果実・木実の扱いを細分化した。

| 系統 | 『正倉院文書』・『延喜式』で言及される原料名 | Cで言えること／別途要する証拠 |
|---|---|---|
| 果樹の果実 | 梅、枇杷、李、梨、棗、桃、柿、橘、柑子、柚子、楊梅子 | **古代史料の食品・菓樹の名称を確認**。『延喜式』の苑池栽培候補（梨・桃・柑・柿・橘等）と諸国貢納の記載を分離。各種の果実加工（果実酒・砂糖煮・蜜煮・乾燥）の成立まで自動認定しない |
| ツル植物・山野果実 | 郁子（ムベ）、蔔子（アケビ）、野ブドウ、甘葛、覆瓮子（イチゴ類） | **果実または甘味資源の古い名称を確認**。苑池での栽培・街路樹には不適な種もあり、列挙から栽培や商品化を確定しない |
| 木実・堅果 | 栗子、胡桃子、榛子、椎子、榧、伊知比古（イチイ） | **古代の採集・貢納・菓子の候補**。椎・榧・イチイを生食可能な同一「ドングリ」とすることは避ける。乾燥・炒る・搗く等の工程は個別史料で検証 |
| 水生・地下資源 | 蓮根、菱子、暑預（ヤマノイモ） | 『延喜式』の「菓子」群は**現代の果物という意味に限定されない**。根茎・水生実・地下茎として原料分類する |
| 加工果実の実証状況 | 搗栗、平栗、干柿子は先行するC節で別途検証済み | 今回の名称列挙を追加の独立食品数として二重計上しない。梅干し・葡萄酒など別工程は各専用史料を要する |

出典：中村太一「[日本古代の街路樹（3．街路樹の果実）](https://company.books-yagi.co.jp/archives/3834/3)」八木書店グループ（『正倉院文書』『延喜式』の果実・菓子・苑池「菓樹」列挙および植物分類の考察）。列挙は古代史料を整理した二次研究であり、原文の個別箇所と植物同定の異説は未照合。

**Cでの判定**：原料・貢納・栽培果樹という存在証拠と、調理済みの果実菓子・飲料を分ける。Bの候補の歴史的存在可能性を補強するだけで実装を許可しない。D–Fは未実施。

**射程の訂正:** 従来Cの815年や鎌倉の上層喫茶の確認は維持するが、それだけを茶の全証拠とする扱いを補正する。一方、1574年定勝寺の「振舞」の既存根拠は仏殿修理の際の供食を示すが、引用された解説だけでは受食者の階層を明記しない。寺院料理・贈答・古代工程の確認を、中世庶民の消費確認へ読み替えない。文化的保持の再判定は選定文書にのみ記録する。

**局所的な注意:** 草戸の原料記録は庶民の接点を補うが、材料が見つかっただけで全調理枝を確定しない。古代の貢納だけによる推測、寺院の献立だけによる一般化、灯明油から食用油への用途移し替えを避ける。救荒食の中世地域別実証と全魚種・全料理書照合は依然未完。従来の確認済み事項の一律撤回は行わない。

## 正本と責務
- **Project（本書）**: 複数Modに跨る原料→製品→消費の関係、未決論点、代替性監査、歴史・既存Modの比較、責務候補を一元化。
- **Agriculture**: 栽培食用作物とその必須一次加工・通常作物料理。MOを基盤にする現行仕様は同リポジトリの Design が正本。
- **Grains / Rice Cultivation / Culture Tea / Wild Food Foraging / 将来の保存・漁業・酒造等**: 各々の現行正式Designを優先。担当境界や統合・移管は本書だけで変更しない。
- **Culture／食事行動**: 食事の多様性・心情・栄養・食卓等を変更する案は、既存仕様と競合しないことを確認し、所有先を定めた後に正式設計へ移す。
- 既に存在する正本の仕様・数値をここで再定義しない。採否確定後は所有Modの Design / XML / C# に反映し、Projectには関係図と参照のみを残す。Docs/Coordination.md は連携・状態専用。

## 乾飯（糒）の歴史資料と監査観点
- 国立国会図書館レファレンス協同データベース（https://crd.ndl.go.jp/reference/entry/index.php?id=1000219137&page=ref_view）は『日本料理由来事典』『日本古代食事典』等を示し、蒸した米を乾燥し水・湯で戻せる携帯保存食と説明する。原著の詳細確認は未実施。
- 小学館『日本大百科全書』「糒」（https://kotobank.jp/word/%E7%B3%92-629846）は、軍防令の兵士への糒備蓄規定、日本書紀の記述、煮る／蒸す→天日干し→水・湯で戻す利用を記す。
- Plenus 米食文化研究所「旅と弁当」（https://www.plenus.co.jp/kome-academy/bento_library/column/column01.html）は古代からの携帯食として言及。いずれも**歴史上の存在と用途の根拠**であり、RimWorldでの独立アイテム採用や性能差の根拠ではない。
- 生米を乾燥させただけのものと混同しない。**調理済みの米飯を乾燥する加工食品**として経路を記録する。保存食品の責務が別Modの場合、Grainsの飯との接続と最終製品の所有先を別途決定する。
- **作者評価（2026-10-26）:** 保存食・携帯保存食は食料大量生産時に相対価値が落ちるが、それでも実装価値がある。量産環境だけで不要と判定せず、初期・遠征・備蓄・非常時等、役割を果たす状況を確認する。これは「全品目追加」「現行料理より高性能にする」「具体的効果値を採用」の承認ではない。

## 醤油に関する決定前監査（採用決定ではない）
1. 「醤油」「たまり」「生垂れ／垂れ味噌」「味噌」「醤」の**時期別の製法・原料・用途**を別々に裏付ける。呼称を同じゲームアイテムにすべきかは後で判断。
2. 調味する料理を具体的に挙げ、その料理は**醤油なしで作れるか／味噌・塩・酢で十分か**を記録。
3. 醤油あり・なしの完成品について、栄養・心情・保存・作業・素材損失・設備・交易の**実ゲーム差**を比較する。根拠のないバフは入れない。
4. 発酵素材から液体を得るなら、味噌の副産物にする方式と専用醸造ラインを比較。どちらも採用未決定。
5. 歴史的重要度と現行システムでの価値・負担を分けて評価し、OH要否を経て表現方法を選ぶ。史実上の存在だけで独立アイテム化を確定せず、固有用途がないだけで除外もしない。文化的に欠けると不自然なら同性能でも残す。

## 横断監査の順序と停止条件
1. **棚卸し・歴史裏付け**: 原料から消費までの経路、品目・製法・用途の年代・地域・階層・普及を確認し、未確認を残す。B/C/Dの進捗は小作業マップに従う。
2. **食文化による選定**: 中世日本の庶民を重視し、候補と文化的保持対象を判断する。歴史重要度による絞り込み結果は[専用文書](FoodHistoricalSelection.md)へ記録し、本台帳に重複した選定結果表を作らない。
3. **現行システムでの価値評価・既存Mod照合**: Vanilla+MO+AMJの実ソース、料理・食事効果、代替性、原料取得から消費までの負担を確認する。MO相当の臓器への良い影響は許容範囲に含むが、具体値は検証して判断する。VE／非VE先行例は[ExistingModAudit](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/blob/main/Docs/Research/ExistingModAudit.md)に従い比較し、VEコンテンツModの必須化・任意互換は行わない。
4. **OH要否判断**: 現行の料理・食事システムで不足する表現と、その重要性、変更の改善・負担を比較する。保存加工の便益を料理OHの便益へ付け替えない。OHは前提でも、同性能問題への必須解でもない。
5. **採否・実装方法**: [現行選定ルール](FoodCultureGameplayDesignConstraints.md)に従い、現行機能で追加、同性能で文化を表現、既存統合、工程集約、承認されたOH、保留・不採用を選ぶ。文化的に欠けると不自然な食品は同性能でも残す。食品の保持と全工程の独立実装は別判断。
6. **所有先へ移管**: 作者が採用した部分だけ所有ModのDesign・実装へ反映する。所有変更はCoordinationで引継ぎ、確定仕様は所有先を正本とする。
7. **検証**: 選定ルールだけで候補採用・数値・OHを承認済みにしない。判断前に必要な実ソース確認と、設計・実装後の最小限の検証を区別し、調査段階で重いゲーム試験を始めない。
